Eventos del episodio

history
Los eventos permiten registrar hitos, acciones, cambios de estado, atenciones, inasistencias, referencias, ingresos, cierres y observaciones relevantes ocurridas durante el episodio de demanda.
warning
Regla central: todo evento debe asociarse a un episodio real. Cuando corresponda, también debe vincularse a la etapa donde ocurrió. No deben existir eventos ficticios, simulados ni generados solo para completar la interfaz.

Relación funcional

account_tree
Episodio → Etapa → Evento → Auditoría

Los eventos permiten reconstruir la historia completa del episodio. Cada acción relevante debe quedar registrada con fecha, tipo de evento, responsable, programa asociado y observación cuando corresponda.

Tipos de eventos esperados

  • Solicitud inicial: hito de origen del episodio o demanda.
  • Contacto con persona: registro de comunicación o intento de contacto.
  • Evaluación: revisión técnica, clínica o administrativa del caso.
  • Ingreso a tratamiento: hito que detiene el KPI de espera.
  • Inasistencia: registro de ausencia a citación o atención programada.
  • Referencia enviada: envío desde un programa de origen a otro receptor.
  • Referencia recibida: recepción de continuidad por el programa receptor.
  • Retroalimentación: evento repetible de comunicación, devolución o revisión.
  • Cierre por causal formal: término administrativo, técnico o clínico.
  • Egreso: salida formal del proceso cuando corresponda.

Datos mínimos de evento

  • Identificador del evento: código único del registro.
  • Identificador del episodio: relación directa con el episodio real.
  • Identificador de etapa: relación con la etapa donde ocurrió, cuando corresponda.
  • Tipo de evento: clasificación funcional del hito registrado.
  • Fecha del evento: fecha y hora en que ocurre o se registra la acción.
  • Usuario responsable: usuario que registra o ejecuta la acción.
  • Programa asociado: programa desde donde se registra el evento.
  • Observación o descripción: detalle técnico o administrativo del evento.
  • Estado o resultado: consecuencia del evento cuando aplique.

Inasistencias

Las inasistencias deben registrarse como eventos trazables del episodio. La regla funcional definida indica que dos inasistencias con el mismo profesional pueden generar cierre por inasistencias, según validación y autorización correspondiente.

person_off
El término correcto para este caso es Cierre por inasistencias, no “Abandono”. Cada inasistencia debe quedar registrada como evento real y no como dato local o comentario sin trazabilidad.
  • Debe registrarse fecha de la inasistencia.
  • Debe quedar asociado el profesional o programa correspondiente.
  • Debe permitir revisar la cantidad de inasistencias acumuladas.
  • Debe permitir aplicar cierre solo cuando exista regla formal.
  • No debe cerrar automáticamente si backend no valida la regla.

Retroalimentación

La retroalimentación debe registrarse como evento repetible. Puede utilizarse para dejar constancia de comunicación, revisión técnica, devolución, coordinación entre programas o información relevante entregada durante el proceso.

forum
La retroalimentación no cierra por sí sola el episodio. Su objetivo es mantener trazabilidad de comunicaciones o revisiones asociadas al caso.

Ingreso a tratamiento

El ingreso a tratamiento es un evento o hito clave porque detiene el KPI de espera del episodio. Debe provenir de un registro real y no debe simularse desde frontend.

play_circle
El KPI de espera se detiene únicamente cuando existe ingreso efectivo a tratamiento registrado en el sistema. Una referencia, derivación o cambio de etapa no debe detener por sí sola el conteo de espera.

No corresponde / No es perfil

Cuando el caso no corresponde o no es perfil para el programa, debe registrarse una causal formal. “No es perfil” puede cerrar de forma inmediata cuando la regla institucional así lo defina y existan avisos o validaciones correspondientes.

  • No corresponde: debe exigir causal formal.
  • No es perfil: puede cerrar inmediatamente según regla definida.
  • Observación: debe dejar fundamento técnico o administrativo.
  • Auditoría: debe registrar usuario, fecha, rol y acción ejecutada.

Eventos asociados a referencias

Las referencias entre programas deben generar eventos trazables dentro del episodio, permitiendo identificar el paso desde el programa de origen hacia el programa receptor.

  • Referencia enviada: programa de origen registra la solicitud de referencia.
  • Referencia recibida: programa receptor toma conocimiento del caso.
  • Referencia observada: se registra observación o devolución cuando corresponda.
  • Referencia aceptada: se confirma continuidad en la etapa receptora.
  • Referencia rechazada: debe existir causal formal y trazabilidad.

Eventos de cierre y egreso

Todo cierre o egreso debe quedar registrado como evento del episodio, indicando causal, fecha, usuario responsable y observación cuando corresponda.

check_circle
El término correcto es Egreso, no “Alta”. El egreso representa una salida formal del proceso de atención cuando corresponde.
  • Cierre por inasistencias.
  • Cierre por no corresponde.
  • Cierre por no es perfil.
  • Cierre administrativo.
  • Cierre técnico o clínico.
  • Egreso formal del proceso.

Auditoría del evento

Cada evento debe dejar trazabilidad de usuario, fecha, rol activo, programa activo, acción realizada y registro afectado. Esto permite reconstruir el historial completo del episodio.

  • Usuario que registra el evento.
  • Rol activo utilizado.
  • Programa activo desde donde se registra.
  • Fecha y hora de creación.
  • Tipo de evento registrado.
  • Registro afectado.
  • Observación o fundamento.

Validaciones esperadas

  • Debe existir persona real.
  • Debe existir episodio real.
  • Debe existir etapa real cuando el evento dependa de una etapa.
  • Debe seleccionarse un tipo de evento válido desde catálogo real.
  • No se deben crear eventos sin fecha o sin responsable.
  • No se deben cargar eventos ficticios para completar la pantalla.
  • No se debe simular guardado si no existe endpoint confirmado.
block
Restricción actual: mientras no estén disponibles las tablas nuevas de eventos, la pantalla debe mostrar únicamente eventos reales entregados por backend. No se deben cargar eventos de ejemplo, arreglos locales, listas simuladas ni mocks.
