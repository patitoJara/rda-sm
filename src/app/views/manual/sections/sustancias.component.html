Sustancias

medication
La sección de Sustancias permite registrar o consultar la sustancia principal y sustancias secundarias asociadas a un episodio de demanda, cuando dicha información exista realmente en backend.
warning
Regla central: las sustancias deben provenir de un catálogo real. No se deben inventar sustancias, usar listas locales ficticias ni guardar selección si no existe tabla o endpoint confirmado para persistir la información.

Relación funcional

account_tree
Catálogo real → Sustancia principal → Sustancias secundarias → Episodio

Las sustancias se asocian al episodio y no a la persona de forma aislada. Esto permite mantener antecedentes históricos por cada demanda o proceso de atención, respetando la trazabilidad del modelo Persona → Episodio → Etapa.

Sustancia principal

Corresponde a la sustancia principal asociada al episodio. Debe seleccionarse desde un catálogo real y quedar vinculada al episodio cuando exista persistencia backend habilitada.

  • Debe existir solo una sustancia principal por episodio, salvo regla backend distinta.
  • Debe provenir de catálogo real entregado por backend.
  • Debe asociarse al episodio real consultado o creado.
  • No debe completarse automáticamente con valores ficticios.
  • No debe guardarse si no existe endpoint de persistencia confirmado.
  • No debe reemplazar información histórica sin autorización.
verified
La sustancia principal debe permitir identificar el antecedente más relevante del episodio, siempre sobre información real y trazable.

Sustancias secundarias

Corresponden a sustancias adicionales asociadas al episodio. Pueden ordenarse según prioridad, relevancia clínica o regla institucional definida.

  • Pueden existir una o más sustancias secundarias.
  • Deben provenir del mismo catálogo real utilizado para la principal.
  • Deben mantener orden cuando corresponda.
  • No deben duplicar la sustancia principal.
  • No deben cargarse desde arreglos locales o datos hardcodeados.
  • No deben mostrarse si backend no entrega información real.

Comportamiento visual esperado

La pantalla puede permitir seleccionar una sustancia principal y ordenar sustancias secundarias de forma visual, siempre dejando claro que la persistencia real depende de tabla y endpoint backend confirmados.

  • Selección principal: radio, botón o selector para marcar la sustancia principal.
  • Orden secundario: click en fila o control visual para asignar orden.
  • Indicadores visuales: chips, números o etiquetas para mostrar prioridad.
  • Validación: impedir duplicar la sustancia principal como secundaria.
  • Bloqueo: deshabilitar guardado si no existe backend disponible.
  • Estado vacío: informar cuando no existan sustancias registradas.
touch_app
El comportamiento visual puede quedar preparado en frontend, pero no debe simular guardado ni crear registros locales si el backend aún no cuenta con tabla y endpoint confirmados.

Validaciones esperadas

  • Debe existir persona real.
  • Debe existir episodio real.
  • Debe existir catálogo real de sustancias.
  • No se debe seleccionar una sustancia inexistente.
  • No se debe duplicar la sustancia principal como secundaria.
  • No se debe guardar si falta endpoint de persistencia.
  • No se debe completar información con datos de prueba.
  • Debe mostrarse estado vacío si no existen sustancias registradas.

Relación con episodio

Las sustancias se asocian al episodio porque forman parte del antecedente de esa demanda específica. Una misma persona puede tener antecedentes históricos diferentes en episodios distintos, por lo que la información debe conservarse vinculada al episodio correspondiente.

  • La sustancia principal pertenece al episodio.
  • Las sustancias secundarias pertenecen al episodio.
  • No deben registrarse como dato aislado de persona sin relación con demanda.
  • El historial debe conservarse por episodio.
  • La modificación debe quedar auditada cuando exista persistencia real.

Relación con etapa y programa

Cuando el modelo backend lo permita, la información de sustancias puede apoyar la gestión del programa responsable de la etapa activa. Sin embargo, la relación principal debe mantenerse con el episodio para no perder continuidad cuando exista referencia entre programas.

sync_alt
Si la persona es referida a otro programa, la información de sustancias no debe duplicarse ni reiniciarse. Debe mantenerse como antecedente del mismo episodio.

Relación con indicadores

Cuando existan datos reales suficientes, las sustancias pueden utilizarse en indicadores estratégicos y listados operativos.

  • Distribución por sustancia principal.
  • Distribución por sustancias secundarias.
  • Casos por programa y sustancia principal.
  • Casos críticos asociados a sustancia principal.
  • Comparación histórica por período.
analytics
Los indicadores por sustancias solo deben calcularse con registros reales. No se deben mostrar gráficos, porcentajes ni totales si no existen datos suficientes en backend.

Catálogo de sustancias

El catálogo de sustancias debe ser administrado desde backend o mantenedor real habilitado. No corresponde crear listas locales para simular opciones dentro del frontend.

  • Debe tener identificador real.
  • Debe tener nombre oficial de sustancia.
  • Debe permitir estado activo/inactivo cuando corresponda.
  • Debe evitar duplicidades.
  • Debe mantenerse trazabilidad de cambios si existe mantenedor.
block
Regla contra catálogos ficticios: no se deben agregar sustancias hardcodeadas para completar la vista. Si el backend no entrega catálogo, debe mostrarse estado pendiente o vacío.

Restricción actual del desarrollo

storage
Mientras no esté confirmada la tabla de sustancias asociadas al episodio, el sistema puede mostrar la estructura visual y catálogos reales disponibles, pero no debe simular guardado ni inventar registros.

Si existen catálogos reales disponibles, pueden utilizarse para visualización o selección controlada. Sin embargo, la acción de guardar debe permanecer bloqueada hasta contar con tabla y endpoint backend confirmados.

Auditoría esperada

Cuando exista persistencia real, toda creación, modificación o eliminación de sustancias asociadas al episodio debe quedar registrada en auditoría.

  • Usuario responsable.
  • Rol activo utilizado.
  • Programa activo cuando corresponda.
  • Fecha y hora de la acción.
  • Sustancia principal anterior y nueva, cuando aplique.
  • Sustancias secundarias modificadas.
  • Motivo u observación si corresponde.
