Episodio / Nueva demanda

folder_open
El Episodio representa una demanda de atención asociada a una persona. Es la unidad central que agrupa etapas, eventos, referencias, sustancias, documentos, alertas, auditoría y resultado final del proceso.
warning
Regla central: una persona puede tener antecedentes históricos, pero solo debe mantener un episodio activo al mismo tiempo. Antes de preparar una nueva demanda, el sistema debe consultar si existe episodio activo real.

Relación funcional

account_tree
Persona real → Episodio activo → Etapas → Eventos → Referencias → Egreso / Cierre

El episodio permite mantener la continuidad del proceso de atención. Sobre él se registran las etapas por programa, eventos relevantes, referencias, sustancias asociadas, documentos, alertas y auditoría.

Datos mínimos del episodio

  • Identificador del episodio: código único del registro de demanda.
  • Identificador de la persona: relación directa con una persona real.
  • Fecha original de solicitud: fecha base para calcular espera y criticidad.
  • Tipo de episodio: clasificación del proceso de demanda.
  • Programa inicial: programa donde se origina la demanda.
  • Programa actual: programa responsable vigente.
  • Estado actual: situación vigente del episodio.
  • Resultado actual: cierre, egreso u otro resultado cuando exista.
  • Observación inicial: antecedente administrativo o técnico de ingreso.

Información operativa

  • Tipo de contacto: forma en que se origina la solicitud.
  • Origen de la solicitud: fuente, institución o vía de ingreso.
  • Derivador o institución remitente: entidad que deriva cuando corresponda.
  • Número de tratamiento previo: antecedente histórico si existe.
  • Estado clínico o administrativo inicial: clasificación inicial del caso.
  • Fecha de ingreso a tratamiento: hito que detiene el KPI de espera.
  • Fecha de cierre o egreso: fecha formal de término cuando corresponda.

Fecha original de solicitud

La fecha original de solicitud es un dato clave del episodio. Esta fecha no debe reiniciarse por referencias, cambios de etapa o cambio de programa. Permite calcular correctamente los días de espera y la condición crítica.

event
La fecha original de solicitud se conserva durante todo el episodio, incluso cuando la persona sea referida desde un programa de origen hacia un programa receptor.

Condición crítica

Un episodio se considera crítico cuando supera los 60 días de espera. El cálculo debe realizarse desde la fecha original de solicitud del episodio.

priority_high
El KPI de espera se detiene únicamente cuando existe ingreso efectivo a tratamiento registrado en el sistema. Una referencia, cambio de etapa o derivación no debe detener por sí sola el conteo de espera.

Cuando existe episodio activo

  • Se muestra la tarjeta de episodio con información real entregada por backend.
  • Se bloquea la opción de preparar una nueva demanda.
  • Se permite revisar la etapa vigente si existe información real.
  • Se permite consultar eventos, referencias y sustancias reales cuando estén disponibles.
  • No se crea un segundo episodio activo para la misma persona.
  • No se reemplaza información real por datos locales o simulados.

Cuando no existe episodio activo

  • Se informa que la persona no tiene episodio activo registrado.
  • Se puede habilitar la opción “Preparar episodio”.
  • El formulario puede quedar disponible como preparación visual.
  • No se debe guardar información hasta contar con backend confirmado.
  • No se genera episodio ficticio.
  • No se usan datos simulados para completar tarjetas.

Preparar episodio

La acción “Preparar episodio” permite abrir visualmente el formulario de nueva demanda cuando la persona existe y no posee un episodio activo. Esta acción no debe confundirse con guardado real si las tablas y endpoints nuevos aún no están confirmados.

edit_note
Mientras el backend no confirme la estructura de persistencia, preparar episodio significa disponer la interfaz para completar información, pero no crear registros reales en base de datos.

Relación con etapas

El episodio contiene una o más etapas por programa. Una etapa representa el paso de la persona por un programa específico dentro del mismo episodio.

  • La primera etapa corresponde al programa inicial.
  • Una referencia no crea un episodio nuevo.
  • Una referencia cierra o finaliza la etapa origen.
  • Una referencia crea una etapa receptora dentro del mismo episodio.
  • La fecha original de solicitud no se reinicia.

Relación con eventos

Los eventos registran hitos relevantes del episodio, tales como solicitud inicial, contacto, evaluación, ingreso a tratamiento, inasistencia, referencia, cierre o egreso.

  • Todo evento debe asociarse a un episodio real.
  • Cuando corresponda, el evento también debe asociarse a una etapa.
  • Las inasistencias deben registrarse como eventos trazables.
  • La retroalimentación debe ser un evento repetible.
  • El ingreso a tratamiento debe quedar como hito real del proceso.

Cierre y Egreso

El episodio debe cerrarse formalmente mediante una causal válida. Cuando corresponde salida del proceso de atención, el término correcto es Egreso, no “Alta”.

check_circle
El egreso representa una salida formal del proceso de atención. El cierre puede responder a causales administrativas, técnicas o clínicas, según la regla definida por el sistema.

Reglas especiales

  • No es perfil: puede cerrar inmediatamente cuando exista causal y avisos correspondientes.
  • No corresponde: debe exigir causal formal.
  • Inasistencias: dos inasistencias con el mismo profesional pueden generar cierre por inasistencias.
  • Reversa: un episodio cerrado no se reabre salvo reversa excepcional autorizada por perfil superior.
block
Restricción actual: mientras no estén disponibles las tablas nuevas del backend, el formulario de episodio debe mantenerse como preparación visual o lectura de datos reales existentes. No debe guardar información ficticia ni simular persistencia.
